Exercice 6 — Complexité et représentation mémoire Chap. 3 (2)

G est d'ordre n et de taille m. On discute la complexité de quatre traitements selon la représentation.

TraitementMatrice d'adjacenceListe de successeurs
Tester si i et j sont adjacentsO(1) : lecture de matAdj[i][j]O(deg(i)), au pire O(n) : parcourir la liste de i (O(1) en moyenne avec un HashSet)
Degré d'un sommetO(n) : somme de la ligne iO(1) : successeurs.size()
Degrés de tous les sommetsO(n²) : n lignes de n casesO(n) si chaque liste connaît sa taille ; O(n + m) si on recompte les éléments

Explications.
  • Le tri de n valeurs par un bon algorithme (tri fusion, tri rapide, List.sort) coûte O(n log n) comparaisons. Un tri naïf (à bulles) coûterait O(n²) comparaisons ; et si chaque comparaison recalcule des degrés avec la matrice (O(n)), on tombe à O(n³) : c'est ce que fait le code fourni (activité 5).
  • C'est ce qui explique le tableau du cours : séquentiel ordonné en O(n²) avec matrice et O(n log n + m) avec listes de successeurs.
  • Conclusion : la matrice gagne pour tester l'adjacence ; les listes gagnent pour tout ce qui concerne les voisins d'un sommet (degré, parcours des voisins) et pour les graphes peu denses.

B. Modélisation du graphe et représentation mémoire

3Contenu de matriceAdj après chargement ; sens du 1
La matrice est de taille n×n et ne contient que des 0 et des 1. Pour chaque ligne du fichier (combinaison d'un étudiant), toutes les paires d'examens de la ligne sont mises à 1 dans les deux sens (matriceAdj[a][b] = matriceAdj[b][a] = 1) : la matrice est symétrique avec une diagonale nulle. 1 en (i, j) signifie que les examens i et j sont incompatibles : au moins un étudiant passe les deux, donc il existe une arête entre i et j dans le graphe de conflits. (Les identifiants du fichier sont diminués de 1 pour correspondre aux indices.)
4Représentation mémoire utilisée
Une matrice d'adjacence int[][] (graphe simple non orienté, sommets numérotés de 0 à n−1), complétée par une liste d'objets Examen dont l'indice est l'identifiant.
5Rôle de getDegre(Examen e)
Elle renvoie le degré de l'examen, c'est-à-dire le nombre d'examens avec lesquels il est incompatible : on parcourt la ligne e.getId() de la matrice et on compte les cases égales à 1. Complexité O(n).

public void attribuerCreneaux_sequentiel(){
    l_creneaux = new ArrayList<Creneau>();
    //les sommets sont traités dans l'ordre du fichier (id croissant)
    for (int i = 0; i < l_exams.size(); i++) {
        Examen e = l_exams.get(i);
        int c = 0;
        boolean test;
        do {
            test = true;
            //on parcourt les sommets déjà traités (j < i)
            for (int j = 0; j < i; j++) {
                if ((matriceAdj[i][j] == 1) && (l_exams.get(j).getCreneauId() == c)) test = false;
            }
            if (!test) c++;
        } while (!test);
        //c vaut au plus l_creneaux.size() : on crée le créneau s'il n'existe pas encore
        if (c >= l_creneaux.size()) l_creneaux.add(new Creneau(c));
        e.attribuerCreneau(l_creneaux.get(c));
    }
}

Étape 3 : étudier les algorithmes fournis et les améliorer

A. Séquentiel ordonné (attribuerCreneaux_sequentiel_ordonne)

  • Instruction qui choisit le prochain sommet : e = getMaxDegre(); (dans la boucle while(nColore < l_exams.size())). Elle renvoie l'examen non coloré de plus haut degré.
  • Même ordre que dans le cours ? Oui : à chaque tour on prend le non coloré de plus haut degré ; en cas d'égalité getMaxDegre garde le premier rencontré (test > strict). Comme les degrés ne changent pas pendant la coloration, c'est exactement l'ordre « degré décroissant, à égalité l'ordre du fichier ».
  • Complexité de la détermination de l'ordre : getMaxDegre parcourt les n examens et appelle getDegre (O(n)) pour chaque candidat non coloré (et de nouveau à chaque nouveau maximum) : O(n²) par appel, donc O(n³) pour les n tours. Le cours (tableau de complexité) annonce O(n²) avec la matrice : les deux versions n'ont pas la même complexité.
  • Calculs inutiles : les degrés sont recalculés à chaque tour alors qu'ils ne changent jamais (et parfois plusieurs fois pour un même candidat). Amélioration : calculer les degrés une seule fois (tableau deg[], O(n²)), puis soit chercher le maximum dans ce tableau (O(n) par tour), soit trier une seule fois les sommets (O(n log n)). Autre gaspillage : pour chaque examen, on repart du créneau 0 et on reparcourt les n examens à chaque créneau testé.
  • Conclusion : un même algorithme (même résultat) peut avoir des implémentations de complexités très différentes ; la complexité dépend de l'implémentation et des structures de données, pas seulement de l'idée. Il faut éviter de recalculer ce qui ne change pas.

B. Welsh et Powell (attribuerCreneaux_WP)

  • Rôle de l'ArrayList ordre : elle contient les indices (identifiants) des examens rangés par degré décroissant : c'est l'ordre de parcours de l'algorithme, sans modifier la liste des examens.
  • Pourquoi ne pas trier l_exams directement ? Parce que le code suppose que l'indice dans l_exams est l'identifiant de l'examen, utilisé aussi comme numéro de ligne dans matriceAdj (l_exams.get(id), matriceAdj[id][j]). Trier la liste casserait la correspondance indice ↔ id ↔ ligne de la matrice. D'où un tri indirect : on trie une liste d'indices.
  • Algorithme de tri utilisé : un tri à bulles (tri par permutations), avec arrêt dès qu'un passage ne permute plus.
  • Complexité : O(n²) comparaisons ; comme chaque comparaison appelle getDegre (O(n)) deux fois, on obtient O(n³) au total (O(n²) comparaisons × O(n)).
  • Plus simple et plus efficace en Java : calculer les degrés une fois dans un tableau, puis trier la liste avec un comparateur : 
    int[] deg = new int[n];
for (int i = 0; i < n; i++) deg[i] = getDegre(l_exams.get(i));      // calculés une seule fois
ArrayList<Integer> ordre = new ArrayList<>();
for (int i = 0; i < n; i++) ordre.add(i);
ordre.sort((a, b) -> deg[b] - deg[a]);                              // tri stable, O(n log n)
    (ou Collections.sort(ordre, comparateur)). Résultat identique (le tri de Java est stable comme le tri à bulles), complexité totale O(n²) pour les degrés puis O(n log n) pour le tri. Vérifié : cette version donne les mêmes créneaux que le code fourni sur les six jeux de données.

C. DSATUR (attribuerCreneaux_DSATUR)

  • Degré de saturation : nombre de couleurs (créneaux) différentes déjà utilisées par les voisins du sommet.
  • Rôle du tableau tab : tab[i] compte combien de voisins de l'examen ont déjà le créneau i. On compte ensuite le nombre de cases non nulles : c'est le nombre de créneaux différents chez les voisins.
  • Pourquoi ne pas compter les voisins colorés ? Parce que plusieurs voisins peuvent avoir le même créneau : trois voisins colorés tous en créneau 1 ne « bloquent » qu'une seule couleur (saturation 1, pas 3).
  • Information réellement mémorisée : l'ensemble des créneaux distincts présents chez les voisins (la multiplicité ne sert à rien).
  • Structure Java adaptée : un ensemble sans doublons : Set / HashSet<Integer>.
  • Code simplifié : 
    public int getDegSaturation(Examen e){
    HashSet<Integer> couleurs = new HashSet<>();
    for (int j = 0; j < l_exams.size(); j++) {
        if ((matriceAdj[e.getId()][j] == 1) && (l_exams.get(j).getCreneau() != null)) {
            couleurs.add(l_exams.get(j).getCreneauId());       // les doublons sont ignorés
        }
    }
    return couleurs.size();
}
    Plus de tableau tab, plus de seconde boucle sur les créneaux. Complexité par appel : de O(k·n) (k créneaux utilisés × n examens) à O(n) : un seul passage sur la ligne de la matrice. Comme k ≤ n, on passe au pire de O(n²) à O(n) par appel. Résultats vérifiés identiques sur les six jeux de données.

Étape 5 : limites de la représentation par matrice

  • Pourquoi getDegre n'est-elle pas dans Examen ? Le degré est une propriété du sommet, mais Examen ne connaît pas ses voisins : les liens sont dans la matrice, attribut de Universite. Seule l'université peut donc calculer le degré. Conclusion : la matrice d'adjacence est une structure extérieure aux objets : peu satisfaisante du point de vue conception objet (les sommets sont « idiots », tout passe par des indices et par la classe Universite).
  • Nombre de cases : n². Complexité mémoire : O(n²).
  • Si chaque examen n'est incompatible qu'avec peu d'autres : la matrice est presque entièrement remplie de 0 (matrice creuse) : n² cases pour très peu d'informations utiles.
  • Représentation plus adaptée : la liste de successeurs : chaque Examen possède une List<Examen> incompatibles (mémoire O(n + m)).
  • Opérations qui en bénéficieraient : getDegre (taille de la liste, O(1) au lieu de O(n)) et donc getMaxDegre, le tri de WP et DSATUR ; getDegSaturation (on ne parcourt que les voisins : O(deg) au lieu de O(n)) ; la recherche d'un créneau compatible dans les trois algorithmes (parcours des voisins seulement). Et la méthode getDegre irait enfin dans la classe Examen.
  • Toujours avantageux ? Non. Si le graphe est dense (beaucoup d'incompatibilités), la matrice n'est plus gaspillée et le test d'adjacence en O(1) est précieux ; les listes demandent plus d'objets. De plus, tester si deux examens précis sont incompatibles devient O(deg) au lieu de O(1). Enfin, changer de représentation a un coût de réécriture.
Activité 6 — Explorer un graphe (wiki) Exploration à présenter
Énoncé résuméUn wiki : on s'intéresse aux liens hypertextes internes ; objectif : visiter toutes les pages accessibles depuis une page A. Mini wiki de 11 pages : A → B, C, D ; B → C, E ; C → F ; D → F ; E → G, K ; F → E, H ; G → A ; H → D, I ; J → F, I (I et K n'ont aucun lien sortant).

1. Modéliser

Sommets = les pages. Arc p → q ⇔ la page p contient un lien hypertexte vers la page q. Le graphe est orienté : un lien de p vers q n'implique pas un lien de q vers p. Les doublons ayant été supprimés et les listes ne contenant que « les autres pages », il n'y a ni arcs multiples ni boucles : c'est un graphe orienté simple.

2. Tenter d'explorer à partir de B

aReprésentation mémoire naturelle
Les données sont des listes de liens par page : la liste de successeurs (par exemple Map<String, List<String>>) est la représentation naturelle.
bExploration depuis B : informations à mémoriser
À chaque étape, on mémorise : (1) les pages vues mais non explorées (à faire), (2) les pages déjà explorées (pour ne pas les refaire). On prend toujours la page vue depuis le plus longtemps.

Ne pas oublier de page : on n'arrête que lorsque la liste des pages vues non explorées est vide, et on explore chaque page de cette liste.

bComment choisir le prochain sommet à explorer ?
En prenant celle qui est dans la liste depuis le plus longtemps (la première ajoutée) : la liste fonctionne comme une file (premier entré, premier sorti). On obtient un parcours en largeur. Si on prenait la dernière ajoutée (pile), on obtiendrait un parcours en profondeur : tout autre choix ferait aussi explorer toutes les pages accessibles, mais dans un autre ordre.
cUne page vue plusieurs fois mais non explorée doit-elle être ajoutée plusieurs fois ? Comment éviter les doublons ?
Non : une seule fois suffit, sinon on l'explorerait plusieurs fois (travail inutile, voire boucle infinie dans les cycles). Exemple : F est vue depuis C puis depuis D (on ne la rajoute pas la seconde fois). Pour éviter les doublons, on marque chaque page « vue » au moment où on l'ajoute et on teste ce marquage avant tout ajout.

4. Structures de données

  • Pages vues non explorées : une file (Queue/ArrayDeque) pour la largeur, une pile pour la profondeur.
  • Déjà vue ? déjà explorée ? Plusieurs solutions : un boolean[] vu indexé par le numéro de page (accès O(1)) si les pages sont numérotées ; un HashSet de pages vues (vus.add(t) renvoie false si t y est déjà : test et ajout en un seul geste) ; ou un attribut d'état dans l'objet Page (non vue / vue / explorée), qui distingue vu et exploré. Une ArrayList avec contains marcherait mais serait en O(n) à chaque test.

5. L'algorithme

Choisir le sommet initial s ← s0
Marquer s0 « vu » ; ajouter s0 à la file AExplorer
Faire
    – s ← retirer le premier sommet de AExplorer
    – Noter que s a été exploré
    – Ajouter les successeurs de s à AExplorer, s'ils ne sont pas encore vus
      (et les marquer « vus »)
Tant que AExplorer n'est pas vide
(fin : les sommets explorés sont tous les sommets accessibles depuis s0)
Version Java testée (parcours en largeur) : 
static List<String> largeur(Map<String, List<String>> succ, String s0) {
    List<String> explores = new ArrayList<>();
    Set<String> vus = new HashSet<>();
    Deque<String> aExplorer = new ArrayDeque<>();
    vus.add(s0);
    aExplorer.addLast(s0);
    while (!aExplorer.isEmpty()) {
        String s = aExplorer.pollFirst();                    // file : le plus ancien d'abord
        explores.add(s);
        for (String t : succ.getOrDefault(s, List.of())) {
            if (vus.add(t)) aExplorer.addLast(t);            // pas de doublon
        }
    }
    return explores;
}
Résultats : depuis B : [B, C, E, F, G, K, H, A, D, I] ; depuis E : [E, G, K, A, B, C, D, F, H, I] ; depuis A : [A, B, C, D, E, F, G, K, H, I] (10 pages, sans J) ; depuis J : toutes les 11 pages. Avec pollLast() (pile) depuis B : [B, E, K, G, A, D, F, H, I, C], même ensemble de pages, autre ordre.
Complexité : chaque sommet est exploré une fois, chaque arc est examiné une fois : O(n + m) avec des listes de successeurs, O(n²) avec une matrice.

Questions du cours (partie 1) Chap. 4 (1)
1Un chemin élémentaire est-il forcément simple ? Et l'inverse ?
Élémentaire ⇒ simple : oui. Si un même arc (x, y) apparaissait deux fois, le chemin passerait deux fois par x : il ne serait pas élémentaire. Simple ⇒ élémentaire : non. Contre-exemple du cours : <(1,2), (2,4), (4,5), (5,2), (2,7)> n'utilise jamais deux fois le même arc, mais passe deux fois par le sommet 2.
2Graphe orienté simple sans boucle : nombre minimal d'arcs d'un circuit simple ?
2 arcs : u → v puis v → u (deux arcs distincts, de sens opposés). Un seul arc ne peut pas revenir à son origine sans être une boucle.
3Graphe simple non orienté : nombre minimal d'arêtes d'un cycle simple ? Et dans un multigraphe ?
Graphe simple : 3 arêtes (un triangle). Avec 2 sommets, il n'y a qu'une arête entre eux, et un cycle simple ne peut pas l'emprunter deux fois. Multigraphe : 2 arêtes suffisent (deux arêtes parallèles entre u et v), et 1 seule si on autorise les boucles.

Activité 7 — Rechercher des chemins Chap. 4 (2) à présenter

Le graphe de l'activité 7 est celui de l'exercice 7 sans l'arc A → C : C n'a aucun prédécesseur. Cela ne change pas l'exploration depuis C (l'arc A → C menait à C, déjà exploré) : les ordres, les parents et les chemins sont les mêmes.

1Le tableau de marquage permet-il de savoir par quel chemin I a été atteint depuis C ? L'ordre de découverte suffit-il ?
Non, dans les deux cas. Le marquage dit seulement qu'I a été découvert. L'ordre de découverte (C, B, D, G, H, A, E, J, I) ne dit pas depuis quel sommet chacun a été découvert : I aurait pu venir de E ou de J.
2Information minimale à conserver ?
Pour chaque sommet x, le sommet y depuis lequel x a été découvert : son parent dans le parcours. Un seul sommet par case suffit, car un sommet n'est découvert qu'une fois (il est marqué aussitôt).

« — » : F n'est pas découvert. Le tableau de l'énoncé prévoit une colonne K, qui n'existe pas dans ce graphe (10 sommets, de A à J).

4Chemin de C à I à partir du tableau des parents
On part de I et on remonte : parent(I) = E, parent(E) = D, parent(D) = C, la racine. On lit la suite à l'envers : C → D → E → I (3 arcs).
5Graphe formé des arcs parent → sommet : qu'obtient-on ?
Une arborescence de racine C : C est la seule source, chaque autre sommet découvert a exactement un prédécesseur (son parent), et il existe un unique chemin de C à chacun. Elle a 9 sommets (F n'en fait pas partie) et 8 arcs.
6File et pile donnent-elles la même arborescence ? Des chemins de même longueur ?
Non : avec la pile, A est découvert depuis I et I depuis J. Les chemins reconstruits n'ont donc pas forcément la même longueur. C → I fait 3 arcs dans les deux cas (C-D-E-I avec la file, C-H-J-I avec la pile), mais pour aller à A : C → B → A (2 arcs) avec la file contre C → H → J → I → A (4 arcs) avec la pile.
7Quel parcours garantit un nombre minimal d'arcs ?
Le parcours en largeur (BFS) : il découvre les sommets par distance croissante (tous ceux à 1 arc, puis à 2 arcs…). Le premier chemin par lequel il atteint un sommet est donc un plus court chemin en nombre d'arcs.
Exercice 8 — Connexité et composantes connexes Chap. 4 (3)
1Graphe non orienté : sommets découverts par une exploration depuis s₀ ?
Exactement les sommets reliés à s₀ par une chaîne, c'est-à-dire la composante connexe CC(s₀). En non orienté, « atteignable » et « connecté » sont la même chose.
2Algorithme : le graphe est-il connexe ? 
Choisir un sommet quelconque s0
Explorer depuis s0 (BFS ou DFS) en comptant les sommets découverts
Si nombre de sommets découverts = ordre du graphe : connexe
Sinon : non connexe
3Algorithme : toutes les composantes connexes 
Marquer tous les sommets « non découverts » ; composantes ← liste vide
Pour chaque sommet s :
    Si s n'est pas découvert :
        nouvelle ← liste vide
        Explorer depuis s : chaque sommet découvert est marqué et ajouté à nouvelle
        Ajouter nouvelle à composantes
Retourner composantes
Le marquage est commun à toutes les explorations : un sommet déjà rangé dans une composante n'est jamais exploré à nouveau. On fait une exploration par composante, et le coût total reste O(n + m) avec des listes de successeurs.

public ArrayList<Sommet> explorerLargeur(Sommet s){
    ArrayList<Sommet> l_decouverts=new ArrayList<Sommet>();
    Queue<Sommet> file=new ArrayDeque<Sommet>();
    ArrayList<Boolean> marque=new ArrayList<Boolean>(l_sommets.size());
    for(int i=0;i<l_sommets.size();i++){
        marque.add(i,false);
    }
    file.add(s);
    marque.set(s.getId(),true);
    l_decouverts.add(s);
    while(!file.isEmpty()){
        s=file.poll();
        for(Sommet succ:s.getSuccesseurs()){
            if(!(marque.get(succ.getId()))){
                marque.set(succ.getId(),true);
                file.add(succ);
                l_decouverts.add(succ);
            }
        }
    }
    return l_decouverts;
}

public ArrayList<Sommet> BFS_Parents(Sommet s){
    ArrayList<Sommet> l_parents=new ArrayList<Sommet>(l_sommets.size());
    Queue<Sommet> file=new ArrayDeque<Sommet>();
    ArrayList<Boolean> marque=new ArrayList<Boolean>(l_sommets.size());
    for(int i=0;i<l_sommets.size();i++){
        marque.add(i,false);
        l_parents.add(i,null);
    }
    file.add(s);
    marque.set(s.getId(),true);
    while(!file.isEmpty()){
        s=file.poll();
        for(Sommet succ:s.getSuccesseurs()){
            if(!(marque.get(succ.getId()))){
                marque.set(succ.getId(),true);
                l_parents.set(succ.getId(),s);
                file.add(succ);
            }
        }
    }
    return l_parents;
}

public ArrayList<Sommet> DFS_Parents(Sommet s){
    ArrayList<Sommet> l_parents=new ArrayList<Sommet>(l_sommets.size());
    Stack<Sommet> pile=new Stack<Sommet>();
    ArrayList<Boolean> marque=new ArrayList<Boolean>(l_sommets.size());
    for(int i=0;i<l_sommets.size();i++){
        marque.add(i,false);
        l_parents.add(i,null);
    }
    pile.push(s);
    marque.set(s.getId(),true);
    while(!pile.isEmpty()){
        s=pile.pop();
        for(Sommet succ:s.getSuccesseurs()){
            if(!(marque.get(succ.getId()))){
                marque.set(succ.getId(),true);
                l_parents.set(succ.getId(),s);
                pile.push(succ);
            }
        }
    }
    return l_parents;
}

public ArrayList<Sommet> retrouverChemin(Sommet s1,Sommet s2,ArrayList<Sommet> l_parents){
    ArrayList<Sommet> chemin=new ArrayList<Sommet>();
    Sommet courant=s2;
    while(courant!=null && courant!=s1){
        chemin.add(0,courant);
        courant=l_parents.get(courant.getId());
    }
    if(courant==null){
        return new ArrayList<Sommet>();
    }
    chemin.add(0,s1);
    return chemin;
}

DFS_Parents reprend explorerProfondeur_it (avec une pile) avec une seule ligne en plus : l_parents.set(succ.getId(), s). Les parents doivent avoir été calculés depuis s1 : un tableau de parents ne sert qu'à reconstruire des chemins qui partent de sa racine.

III. Étude de la faible connexité

7testerConnexite et chercherCC
Pour un graphe orienté, on ignore le sens des arcs : un sommet t est voisin de s si t est un successeur de s ou si s est un successeur de t. Sinon, un graphe comme l'exercice 7 paraîtrait non connexe depuis C (F n'y est pas atteignable), alors qu'il est faiblement connexe. testerConnexite se contente de demander les composantes à chercherCC : le graphe est connexe s'il n'y en a qu'une.
public boolean testerConnexite(){
    return chercherCC().size()==1;
}

public ArrayList<ArrayList<Sommet>> chercherCC(){
    ArrayList<ArrayList<Sommet>> l_composantes=new ArrayList<ArrayList<Sommet>>();
    ArrayList<Boolean> marque=new ArrayList<Boolean>(l_sommets.size());
    for(int i=0;i<l_sommets.size();i++){
        marque.add(i,false);
    }
    for(Sommet depart:l_sommets){
        if(!(marque.get(depart.getId()))){
            ArrayList<Sommet> composante=new ArrayList<Sommet>();
            Queue<Sommet> file=new ArrayDeque<Sommet>();
            file.add(depart);
            marque.set(depart.getId(),true);
            composante.add(depart);
            while(!file.isEmpty()){
                Sommet s=file.poll();
                for(Sommet t:l_sommets){
                    // t est voisin de s si t est un successeur de s ou si s est un successeur de t
                    if(!(marque.get(t.getId())) && (s.getSuccesseurs().contains(t) || t.getSuccesseurs().contains(s))){
                        marque.set(t.getId(),true);
                        file.add(t);
                        composante.add(t);
                    }
                }
            }
            l_composantes.add(composante);
        }
    }
    return l_composantes;
}

IV. Réflexion et amélioration des représentations

9Difficultés liées à l'identification des sommets
Le code suppose que les identifiants sont exactement 0, 1, …, n − 1 et dans l'ordre du fichier : l_sommets.get(id) et la liste marque en dépend. Avec des identifiants quelconques (numéros non contigus, noms de pages, codes de stations), il faut une table de correspondance, par exemple une HashMap<String, Sommet> du nom vers le sommet, ou un indice interne distinct de l'identifiant « métier ». Il faut aussi refuser les doublons d'identifiant.
10Pourquoi le modèle n'est-il pas adapté aux multigraphes ? Comment décrire un chemin ?
Une liste de successeurs ne stocke que des sommets : deux arcs parallèles de a vers b donnent deux fois b dans la liste, sans qu'on puisse les distinguer (ligne de métro, durée…). Les parcours restent corrects pour l'atteignabilité, mais un chemin décrit comme une suite de sommets est ambigu. Dans un multigraphe, un chemin doit être décrit comme une suite d'arcs : a –(arc 3)→ x –(arc 7)→ b.
11Modèle pour les multigraphes et les itinéraires
  • Graphe : orient, l_sommets : ArrayList<Sommet>, l_arcs : ArrayList<Arc> ; méthodes charger, explorerLargeur, BFS_Parents, retrouverItineraire, chercherCC.
  • Sommet : id, nom, arcsSortants : ArrayList<Arc> (au lieu d'une liste de sommets) ; méthode ajouterArcSortant(Arc a).
  • Arc : id, depart : Sommet, arrivee : Sommet, informations éventuelles (ligne, durée) ; deux arcs parallèles sont deux objets distincts.
  • Itineraire : depart : Sommet, arrivee : Sommet, arcs : ArrayList<Arc> ; méthodes getLongueur() (nombre d'arcs) et afficher().
  • Associations : Graphe ◆— * Sommet, Graphe ◆— * Arc, Arc → 1 Sommet (départ) et → 1 Sommet (arrivée), Itineraire → * Arc (ordonnés). Pour reconstruire un itinéraire, on mémorise l'arc parent de chaque sommet (l'arc par lequel il a été découvert) au lieu du sommet parent.
12Tenir compte de pondérations sur les arcs
Ajouter un attribut poids (durée, distance, coût) dans la classe Arc ; la longueur d'un itinéraire devient la somme des poids de ses arcs. Attention : le BFS minimise le nombre d'arcs, pas la somme des poids. Un chemin de 3 arcs courts peut être meilleur qu'un chemin d'un seul arc très long : il faudra d'autres algorithmes de plus court chemin pondéré.

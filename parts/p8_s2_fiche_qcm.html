Algorithmes : exhaustif, glouton, heuristique

NotionÀ retenir
Exhaustif (brute force)teste toutes les combinaisons ; solution optimale garantie ; explosion combinatoire (exponentiel)
Gloutonmeilleur choix local à chaque étape, sans retour en arrière ; rapide, simple ; optimum non garanti
Heuristiquerègle de choix (intuition) pour trouver vite une bonne solution, sans garantie d'optimalité ; guide les choix sans changer l'objectif

Complexité

  • Complexité temporelle : nombre d'opérations en fonction de la taille n, notée O(f(n)). Familles : O(1), O(log n), O(n), O(n log n), O(n²), O(n³), O(2ⁿ), O(n!).
  • Repères : recherche linéaire O(n) ; tri par insertion O(n²) ; tri rapide O(n log n). À n = 1 000 000 : O(n log n) ≈ 20 ms, O(n²) ≈ 17 min, O(n³) ≈ 32 ans ; l'exponentiel est inutilisable dès n = 100.
  • Algorithme raisonnable = polynomial. Problème facile = admet un algorithme déterministe raisonnable. Probablement difficile = personne ne sait prouver qu'il est facile (ex. nombre chromatique).

  • Saturation d'un sommet = nombre de couleurs différentes chez ses voisins (⚠ pas le nombre de voisins colorés).
  • Tous sont des heuristiques gloutonnes : toujours une coloration propre, optimum non garanti. Le séquentiel est « très dépendant de l'ordre ».
  • Encadrement : ω(G) ≤ χ(G) ≤ 1 + Δ(G) (ω = taille de la plus grande clique, Δ = degré maximum). Déterminer k-colorabilité, χ(G) ou une coloration optimale : problèmes difficiles.

Améliorer le code Java

  • Ne pas recalculer ce qui ne change pas : calculer les degrés une fois (tableau), puis trier avec ordre.sort((a, b) -> deg[b] - deg[a]) (tri stable en O(n log n)) au lieu d'un tri à bulles O(n²) qui rappelle getDegre.
  • Trier une liste d'indices (tri indirect) et non la liste d'objets, quand l'indice sert d'identifiant (ligne de la matrice).
  • Saturation avec un HashSet<Integer> : un seul passage O(n) au lieu de O(k·n).
  • Matrice : O(n²) mémoire, creuse si peu d'incompatibilités ; les sommets ne connaissent pas leurs voisins (peu « objet »). Liste de successeurs : degré O(1), parcours des voisins direct ; mais pas toujours avantageuse (graphe dense, tests d'adjacence).

Explorer un graphe (activité 6)

  • Wiki : sommets = pages, arc p → q = lien de p vers q ⇒ graphe orienté (simple si pas de doublons), stocké en listes de successeurs.
  • Trois états : non vue, vue non explorée, explorée. On ne découvre que les pages accessibles (J n'est jamais découverte depuis B ou E).
  • Algorithme : marquer le départ vu et l'ajouter à AExplorer ; tant que non vide : retirer s, l'explorer, ajouter ses successeurs pas encore vus (en les marquant vus).
  • File (FIFO) ⇒ parcours en largeur ; pile (LIFO) ⇒ parcours en profondeur. Marquer « vu » à l'ajout évite doublons et boucles. Complexité O(n + m) avec listes de successeurs.
  • Structures : file/pile pour AExplorer ; HashSet (ou boolean[]) pour les pages vues.
Pièges classiques
  • Saturation = couleurs différentes chez les voisins, pas le nombre de voisins colorés.
  • Welsh-Powell = une couleur à la fois ; séquentiel ordonné et DSATUR = un sommet à la fois.
  • Un résultat obtenu par un algorithme glouton n'est pas prouvé minimal : il faut une borne inférieure (clique) ou le brute force.
  • Brute force : exact mais exponentiel ; « raisonnable » = polynomial.
  • Exploration : une page vue plusieurs fois n'est ajoutée qu'une fois à la liste ; on ne découvre pas les pages non accessibles.
